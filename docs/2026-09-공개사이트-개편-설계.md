## 1. 성공사례 — 49억을 20억으로 줄여 쓰던 지표의 정정

### ① 현재 상태

화면은 이미 2개 갈래(`/success/funding`, `/success/bidding-entry`)로 완성. 그러므로 레이아웃은 손대지 않고 **수치만** 교체하는 작업.

수치가 네 군데에 각각 하드코딩돼 있어 서로 어긋난 상태이며, 실제 실적 대조 결과 세 종류의 오류 발견.

| 유형 | 내용 | 영향 |
|---|---|---|
| 근거 없는 사례 | `서울 공공서비스 용역 12억 낙찰` | 실재하지 않는 건 |
| 단계 오표기 | 1차 서류합격을 `최종 선정`으로 기술 (2건) | 공개 사이트 신뢰도 위험 |
| 대폭 누락 | 입찰 낙찰 26억 5천 전액 미노출 | 최대 실적 미활용 |
| 기준 혼용 | `헤드라인`이 사례마다 단일 최대액·총액을 오감 | 사례 간 비교 불가 |

> 데이터가공 지원사업 `5,500만`은 **사이트 값이 정확**. 대표 실적 리스트 쪽에 `5.5백만 원`으로 적혀 있어 오해를 부른 것이므로, 리스트를 `5,500만 원`으로 고쳐 둘 것.

**② -3c. 대표 동행 사례 — 더블유포지션 상세 화면 신설**

더블유포지션 건은 문서 한 벌을 납품한 사례가 아니라 **아이템 설계부터 자본 조달까지 이어서 수행한 사례**. IR 자료만 4차례 제작하며 단계별로 다듬은 이력이 있으므로, 다른 사례와 같은 카드 한 장에 담으면 무게가 전달되지 않음.

따라서 `/success/wposition` 상세 화면을 신설하고 흐름 전체를 시간순으로 전개.

```
아이템 설계 ─→ IR 1차 ─→ IR 2차 ─→ IR 3차 ─→ IR 4차
                                              │
                                    투자유치 2억
                                              │
                                      TIPS 선정 8억
                                              │
              후속 6건 3억 9,500만 (초기창업·데이터가공·수출바우처·RISE·창업도시조성·D-TECH)
                                              │
                                누계 13억 9,500만
```

이 사례가 갖는 값어치는 금액이 아니라 **울림의 서비스 전부가 한 고객에게 이어져 들어간 증거**라는 점. 즉 컨설팅(아이템 설계·지원사업 전략)과 비즈니스문서·디자인(IR 4벌)이 따로 파는 상품이 아니라 하나의 흐름임을 보여줌. 3절에서 문의를 3갈래로 나누면 각 갈래가 분리돼 보이므로, 이를 되묶는 장치로서도 기능.

| 화면 요소 | 내용 |
|---|---|
| 머리말 | `아이템 설계부터 투자유치까지, 2년간 함께한 기록` |
| 시간순 전개 | 위 흐름을 단계 카드로 배열, 각 단계에 수행 내용과 결과 명시 |
| IR 4벌 | 6절의 가린 샘플로 제시 — 회차별로 무엇이 달라졌는지 캡션에 기술 |
| 누계 | 13억 9,500만 (투자 2억 + 지원사업 11억 9,500만) |
| 연결 | 각 갈래 문의 화면으로 분기 |

> IR 4벌은 `1차 → 4차` 회차 순으로 배열하고, 회차마다 무엇이 달라졌는지를 캡션 한 줄로 기술.

6절 가림 샘플의 **1순위 대상**도 이 건. 회차별 변화를 보여주면 "문서를 어떻게 다듬는가"가 그대로 드러나므로, 단일 문서 3장을 보여주는 것보다 설득력이 큼.

**② -4. 새 대표 지표 4종**

기존 `20억+` 단독 표기를 폐기하고 성과 전면을 드러내는 4종으로 교체.

| 값 | 문구 | 근거 |
|---|---|---|
| **49억+** | 선정·낙찰·투자 누적 | 21억 4,959만 + 26억 5,000만 + 2억 = **49억 9,959만** |
| **300+** | 누적 컨설팅·제작 | 대표 확정 표기. 원장 집계와 별개 |
| **11억** | 단일 입찰 최대 낙찰 | CJ올리브네트웍스 SI 용역 |
| **8억** | 단일 과제 최대 선정 | TIPS |
| **6건** | 대기업·백화점 입점 합격 | 아래 ②-6 |

큰 숫자 하나로 뭉치면 무엇을 받았다는 것인지 흐려지므로, `49억+` 바로 아래 세 갈래 내역을 함께 노출.

| 갈래 | 금액 | 건수 |
|---|---|---|
| 정부지원사업·R&D | 21억 4,959만 | 23 |
| 입찰·수주 | 26억 5,000만 | 5 |
| 투자유치 | 2억 | 1 |

> `기간` 표기는 `진입 2년` → `2023~2026`으로 정정. 원장 최초 연도가 2023이므로 4개년이 정확.
>
> 누적액 49억 9,959만 — **50억에 41만 원 모자람**. 반올림으로 `50억` 표기 금지. 집계 함수가 억 단위 내림을 수행하므로 현재는 `49억+`이며, 다음 실적 1건만 더해져도 문구 수정 없이 자동으로 `50억+` 전환.

## 2. 상담 신청 — 구글폼 의존을 끊는 수신 전환

### ① 현재 상태

`app/api/contact/route.ts`가 구글폼에 대신 제출하는 방식. 동작 흐름은 아래와 같음.

```
방문자 → /api/contact
           │
           ├─ ① GET  docs.google.com/.../viewform     HTML 내려받기
           ├─ ② HTML에서 정규식으로 fbzx 토큰 추출
           ├─ ③ POST docs.google.com/.../formResponse
           └─ ④ 성공 응답
                    ↓
              구글 시트 적재 → 구글 계정 알림 메일
```

문제는 셋.

**첫째, 유실 가능성.** 구글이 폼 마크업을 바꾸면 ② 단계 정규식이 빈 값을 반환하고 요청 전체가 502로 실패. 방문자에게는 오류가 보이지만 **어디에도 기록이 남지 않아** 누가 문의했는지 알 수 없음.

**둘째, 실패 지점 중복.** 한 번의 접수에 외부 요청이 두 번 발생. 구글 응답 지연이 그대로 방문자 대기 시간에 반영.

**셋째, 요구사항 자체가 불가능.** 알림 수신 주소가 구글 계정 설정에 묶여 있어 저장소 코드로는 변경 불가. 즉 대표가 원하는 `수신 메일 주소 변경`은 현재 방식에서 코드 작업으로 해결되지 않음.

### ② 바꿀 내용

**② -1. 저장을 먼저, 알림을 나중에**

접수 성공 판정을 **DB 저장 성공**으로 옮김. 메일 발송은 실패해도 접수는 이미 보존된 상태이므로 문의가 날아가지 않음.

```
방문자 → /api/contact
           │
           ├─ ① Supabase contact_inquiries INSERT   ← 여기까지 성공하면 접수 완료
           ├─ ② 방문자에게 성공 응답 (즉시)
           │
           └─ ③ Resend 메일 발송 (실패해도 무방, 실패는 로그만)
                  수신처 = CONTACT_NOTIFY_EMAILS 환경변수
```

**② -2. 테이블 설계**

```sql
-- supabase/migrations/<timestamp>_contact_inquiries.sql
create table public.contact_inquiries (
  id            uuid primary key default gen_random_uuid(),
  created_at    timestamptz not null default now(),
  track         text not null,          -- consulting | business-docs | design | etc
  name          text not null,
  phone         text not null,
  email         text,
  message       text not null,
  details       jsonb not null default '{}'::jsonb,  -- 갈래 전용 문항
  notified_at   timestamptz,            -- 메일 발송 성공 시각. null이면 미발송
  notify_error  text,
  source_path   text,                   -- 유입 화면
  requester_key text                    -- 속도 제한 키(해시)
);

alter table public.contact_inquiries enable row level security;
-- 익명 조회 차단. 서버 라우트는 service role 키로만 접근.
```

`details`를 `jsonb`로 둔 이유는 3절의 갈래별 문항이 서로 다르기 때문. 문항이 늘어도 마이그레이션 없이 수용 가능.

**② -3. 수신 주소를 환경변수로**

```
CONTACT_NOTIFY_EMAILS=woolim@woolimcompany.kr,wlc_0109@naver.com
RESEND_API_KEY=
RESEND_FROM=울림컴퍼니 상담신청 <noreply@woolimcompany.kr>
```

쉼표로 나눈 복수 주소 지원. 이로써 앞으로 수신처 변경은 **Vercel 환경변수 수정만으로 완료**되며 배포조차 불필요.

**② -4. 메일 본문 규격**

| 위치 | 내용 |
|---|---|
| 제목 | `[상담신청] {갈래} · {이름} · {날짜}` |
| 본문 상단 | 이름 / 연락처 / 이메일 / 유입 화면 |
| 본문 중단 | 갈래 전용 문항 전체 (`details` 펼침) |
| 본문 하단 | 문의 내용 원문 |
| `Reply-To` | 방문자 이메일 (입력 시) — 회신 버튼으로 바로 답장 가능 |

**② -5. 발송 대행사 선정 근거**

Resend 무료 구간은 **월 3,000통 / 일 100통 / $0**, 유료 Pro는 월 50,000통에 $20. [Resend 요금 안내](https://resend.com/pricing) 월 상담 신청이 100건 안쪽이므로 무료 구간으로 충분.

전제 조건은 `woolimcompany.kr` 도메인 인증(SPF·DKIM DNS 레코드 등록) 1회. 인증 없이는 발신 도메인이 제한됨.

**② -6. 구글폼 처리**

전환 직후 삭제하지 않고 **2주간 병행 운영** 후 제거 권고. 기존 폼 응답 시트는 그대로 보존하되, 신규 접수만 DB로 유입.

- 1단계 — DB 저장 + 메일 발송 + 구글폼 제출 **동시** 수행
- 2단계 — 2주 뒤 양쪽 건수 대조, 일치 확인
- 3단계 — 구글폼 제출 코드 및 `FORM_ID` 상수 제거

**② -7. 관리자 목록 화면 (선택)**

`/admin/inquiries` 신설. 기존 `lib/auth.ts`의 `ADMIN_EMAILS` 인증을 그대로 사용. 목록·상세·처리 상태 표시. 1·2단계 이후 별도 착수 가능.

### ③ 건드릴 파일

```
신설  supabase/migrations/<ts>_contact_inquiries.sql
신설  lib/contact/store.ts               DB 저장
신설  lib/contact/notify.ts              Resend 발송
신설  lib/contact/notify.test.mjs        본문 조립·수신처 파싱 검증
수정  app/api/contact/route.ts           흐름 교체, 속도 제한·허니팟 유지
수정  .env.example                       RESEND_*, CONTACT_NOTIFY_EMAILS 추가
수정  package.json                       resend 의존성
```

기존 속도 제한(`시간당 10회`)과 허니팟(`website` 항목) 방어는 **그대로 유지**. 검증 순서는 허니팟 → 속도 제한 → 길이 검사 → 저장 순.

### ④ 완료 판정

- 정상 접수 시 `contact_inquiries`에 행 1개 생성, `notified_at`이 채워짐
- `RESEND_API_KEY` 제거 후 접수 시에도 **행은 생성되고 200 응답** 반환, `notify_error`에 사유 기록
- DB 연결 실패 시에만 502 반환
- 허니팟 채워진 요청은 행 생성 없이 200 반환
- `CONTACT_NOTIFY_EMAILS`에 쉼표 구분 2개 지정 시 양쪽 모두 수신
- `npm run verify` 전체 통과

## 3. 문의하기 — 11개 항목을 3개 갈래로 가르는 분리

### ① 현재 상태

`/contact` 단일 화면에 `ContactForm` 하나. 상담 분야는 `select` 1개에 11개 항목이 한꺼번에 나열.

문제는 둘. 첫째, 방문자가 11개 중 무엇이 자기 상황인지 판단해야 하는 부담 발생. 둘째, 어느 분야를 골라도 받는 정보가 `이름 / 연락처 / 이메일 / 문의내용` 넷뿐이라 **상담 전 선별 불가**. 예컨대 정부지원사업 문의를 받아도 업력·매출·근로자 수가 없으면 자격 판단 자체가 성립하지 않음.

덧붙여 사업영역 메뉴는 이미 3갈래인데 문의 화면만 1개라 메뉴 짜임새가 어긋난 상태.

### ② 바꿀 내용

**② -1. 사업영역과 1:1 대응하는 4개 화면**

| 경로 | 대응 사업영역 | 흡수할 기존 항목 |
|---|---|---|
| `/contact` | (허브) | 갈래 선택 + 기타문의 |
| `/contact/consulting` | 경영컨설팅 | 정부지원사업, 정책자금, 기업인증 3종, 연구소 설립, 종합 경영컨설팅 |
| `/contact/business-docs` | 비즈니스문서·PPT | 사업계획서 IR, 소개서·제안서 PPT |
| `/contact/design` | 디자인서비스 | 디자인 서비스 |

서비스 화면 하단 `ContactBand`가 각 대응 문의 화면으로 직행하도록 연결 변경. 따라서 방문자는 읽던 맥락 그대로 문의 진입 가능.

**② -2. 공통 문항 + 갈래 전용 문항**

공통 5개는 전 화면 동일, 전용 문항만 갈래별로 교체. 전용 문항 값은 2절 `details` jsonb에 그대로 적재.

| 갈래 | 전용 문항 | 목적 |
|---|---|---|
| consulting | 세부 분야 · 업력 · 상시근로자 수 · 직전년도 매출 · 희망 착수 시기 | 지원사업 자격 사전 판정 |
| business-docs | 문서 종류 · 예상 분량 · 납기 희망일 · 원고 보유 여부 | 견적·일정 산출 |
| design | 디자인 종류 · 수량·규격 · 납기 희망일 · 브랜드 가이드 보유 여부 | 작업량 산출 |

> **[대표 확인]** 위 전용 문항은 제안값. 실제 상담에서 매번 되묻는 항목이 따로 있으면 교체 요망.

**② -3. 부품 재사용 설계**

화면 4개를 각각 만들면 공통 문항이 네 벌로 갈라져 유지가 어려워짐. 그러므로 **문항 정의는 데이터로, 화면은 하나로** 처리.

```
data/contact-tracks.ts        갈래별 문항 정의(라벨·타입·필수·선택지)
        ↓
components/ContactForm.tsx    track prop 받아 전용 문항을 동적 렌더
        ↓
app/contact/[track]/page.tsx  generateStaticParams로 3개 화면 생성
```

`[track]` 동적 경로를 쓰되 `generateStaticParams`로 고정 3개만 생성. 정의되지 않은 갈래는 `notFound()` 반환.

**② -4. 허브 화면 재편**

`/contact`는 폼 대신 **갈래 선택 카드 3장 + 즉시 연결 수단**으로 전환. 기타문의만 허브에서 직접 접수.

| 요소 | 내용 |
|---|---|
| 카드 3장 | 갈래명 · 한 줄 설명 · 대표 실적 1건 · 진입 버튼 |
| 즉시 연결 | 전화 · 카카오 채널 · 이메일 (기존 `channels` 유지) |
| 기타문의 | 접이식 폼으로 하단 배치 |

**② -5. 검색 노출 처리**

화면이 4개로 늘어나므로 각 화면에 고유 `metadata`와 `canonical` 부여. `FAQPage` 스키마는 허브에만 유지하고 갈래 화면에는 `BreadcrumbList`와 `ContactPoint` 적용. `app/sitemap.ts`에 3개 경로 추가.

### ③ 건드릴 파일

```
신설  data/contact-tracks.ts
신설  data/contact-tracks.test.mjs       문항 정의 무결성 검증
신설  app/contact/[track]/page.tsx
수정  app/contact/page.tsx               허브로 재편
수정  components/ContactForm.tsx         track prop 수용, 동적 문항

```

### ④ 완료 판정

- `/contact/consulting`, `/contact/business-docs`, `/contact/design` 세 경로가 200 반환
- `/contact/unknown` 이 404 반환

- `npm run verify` 전체 통과

## 5. PPT 포트폴리오 — 승인 목업 세트 재사용

### ① 현재 상태

**공개 포트폴리오 쪽** — `public/images/projects/<id>/` 아래 프로젝트당 5개 파일(`thumbnail.webp`, `cover.*`, `slide-01~03.webp`). 전부 2560×1440 단일 규격이며, 한 장 안에 슬라이드 3~6개를 합쳐 납작하게 만든 형태. 생성 스크립트는 없고 수작업 산출물. 프로젝트 50건.

가독성 문제가 분명함. 2560×1440 한 장에 6개를 넣으면 슬라이드 하나당 실효 해상도가 약 780×440이고, 갤러리 카드로 줄어들면 본문 글자 판독이 불가능. 더구나 상하좌우 여백이 30%를 넘어 실제 내용 영역이 좁음. `slide-01`처럼 위 3장·아래 2장 중앙정렬인 판은 정렬 규칙도 일정하지 않음.

**콘텐츠 관리자 쪽** — `lib/portfolio/approved-mockup-*`에 규격별 목업 세트가 이미 완성 상태. 대표가 요청한 재사용 대상이 바로 이것.

| 규격 | 세트 ID | 최소 고유 장표 | 산출물 |
|---|---|---|---|
| 16:9 | `approved-16x9-suite` | **8장** | `thumbnail.jpg` 1080×1080 + 본문 4종 1600×900 |
| A4 가로 | `approved-a4-landscape-suite` | **7장** | 동일 |
| A4 세로 | `approved-a4-portrait-suite` | **7장** | 동일 |

호출부는 단일 함수로 정리돼 있어 공개 쪽에서 그대로 끌어 쓸 수 있음.

```ts
renderApprovedMockupSuite({
  aspectClass: "16:9",
  slides: [{ index: 0, buffer }, ...],   // 낱장 이미지 버퍼
  coverIndex: 0,
  title: "판토모나 브랜드 소개서",
})
// → { assets: [thumbnail, short-main, short-detail-1~3] }
```

### ② 갈림길 — 입력 형식의 불일치

승인 세트는 **낱장 슬라이드**를 입력으로 받으며, 다음 세 가지를 강제.

1. 서로 다른 장표 8장(16:9) 또는 7장(A4) 이상
2. 각 장표 가로세로비가 템플릿 비율과 **0.5% 이내** 일치 — 늘이거나 잘라서 맞추지 않음
3. 내용이 동일한 장표 중복 금지 (SHA-256 대조)

그런데 현재 공개 포트폴리오 이미지는 **이미 합쳐진 보드**. 따라서 그대로는 되먹일 수 없으며, 원본 낱장 확보 여부가 경로를 가름.

**대표 확인 결과 — 원본 낱장 보유, 네이버웍스 드라이브에 보관.** 따라서 경로 A로 확정하며 아래 ④ 경로 B는 폐기.

**② -1. 드라이브 연동은 이미 구축된 상태**

원본을 받아 낱장으로 쪼개는 길은 새로 만들 필요가 없음. 2026-07 블로그 포트폴리오 자동화용으로 이미 구축된 파이프라인이 그대로 존재.

| 단계 | 이미 있는 것 |
|---|---|
| 인증 | `app/api/admin/naver-works/connect·callback` — 구성원 OAuth, `file.read` 읽기 전용 |
| 탐색 | `lib/naver-works/drive-sync.ts` → `naver_works_drive_files` 색인 |
| 후보 선정 | `lib/naver-works/portfolio-selection.ts` → `portfolio_candidates` |
| 낱장 변환 | PC 워커(PowerPoint) → `portfolio_image_sets` |
| 목업 | `portfolio_mockup_sessions` + 승인 목업 세트 |

즉 5절의 실제 일은 **이미 뽑혀 나오는 낱장을 공개 포트폴리오 쪽으로도 내보내는 출구 하나**를 다는 것. 설계 문서는 `docs/naver-works-portfolio-automation-plan.md` 참고.

**② -2. 걸림돌 — `블로그 중복 제외` 규칙**

기존 파이프라인은 `기존 블로그와 중복된 프로젝트는 제외`하도록 설계됨. 그런데 공개 포트폴리오 50건은 대부분 **이미 블로그에 올린 프로젝트**이므로, 그대로 돌리면 정확히 이 규칙에 걸려 후보에서 빠짐.

따라서 자동 선정과 별개로 **지정 재굽기 모드**를 신설.

| | 기존 자동 선정 | 지정 재굽기 (신설) |
|---|---|---|
| 대상 | 드라이브 전체에서 신규 프로젝트 | 대표가 고른 드라이브 폴더 목록 |
| 중복 규칙 | 블로그 중복 제외 | **적용 안 함** |
| 결과물 | 블로그 초안 + 검토 요청 | 공개 포트폴리오 목업 세트 |
| 공개 | 검토 필요 상태 | 검토 필요 상태 (동일) |

두 모드가 같은 `portfolio_image_sets`를 공유하므로, 같은 프로젝트를 블로그용·포트폴리오용으로 두 번 변환하지 않도록 **이미 변환된 낱장이 있으면 재사용**.

**② -3. 매핑 표 — 공개 포트폴리오 ↔ 드라이브 폴더**

현재 `portfolioProjects`의 `id`(`onnuri-store` 등)와 드라이브 폴더 사이에 연결 고리가 없음. 지정 재굽기를 하려면 이 매핑이 먼저 필요.

```ts
// data/portfolio-drive-map.ts (신설)
export const portfolioDriveMap = {
  "onnuri-store": { driveFolderId: "…", aspectClass: "16:9" },
  // 50건
} as const;
```

> **[대표 확인]** 50건 각각의 드라이브 폴더 위치. Codex가 드라이브 색인(`naver_works_drive_files`)에서 상호명으로 후보를 찾아 표를 채우고, 대표가 맞는지만 확인하는 방식 권고.

## 6. 사업계획서 샘플 — 가린 원본으로 짜임새만 드러내기

### ① 현재 상태

사업계획서 자산은 **이미 존재**. `data/content.ts`에 `category: "ir"` 프로젝트 14건이 등록돼 `/portfolio/business-ir`에서 노출 중.

> UYU K-뷰티 투자제안서 · 파미티 Spatial AI 투자제안서 · 영화사 오픈시네마 콘텐츠 투자제안서 · 롯데웰푸드 키즈카페 · 미사동커피공동체협동조합 · 모란막걸리 · 청곡종합사회복지관 · 더신선팜 아쿠아포닉스 · 하임 셀프포토 · 지붕위의호랑이 외

문제는 **자산 부재가 아니라 동선 단절**.

| 화면 | `/portfolio/business-ir` 연결 |
|---|---|
| `/portfolio` 허브 | ✓ |
| 상단 메뉴 | ✓ |
| 홈 | ✓ |
| `/services/consulting` | **없음** |
| `/success/funding` | **없음** |

즉 컨설팅 문의로 들어온 방문자는 사업계획서 실물을 한 번도 보지 못한 채 이탈. 반면 디자인 쪽은 `/services/design` → `/portfolio/design` 동선이 살아 있음.

더불어 `/portfolio/business-ir`은 디자인과 동일한 `ProjectGallery` 부품을 그대로 사용하므로 **선정 여부가 전혀 드러나지 않음**. 디자인 포트폴리오는 완성물이 곧 증거이나, 사업계획서는 `선정됐는가`가 증거라는 차이가 화면에 반영되지 않은 상태.

### ② 바꿀 내용

**② -1. 끊긴 동선 잇기**

| 위치 | 추가할 연결 |
|---|---|
| `/services/consulting` 본문 하단 | `사업계획서 실물 보기` → `/portfolio/business-ir` |
| `/success/funding` 각 사례 카드 | 해당 사업계획서 샘플 → `/portfolio/business-ir#<slug>` |
| `/portfolio/business-ir` 각 카드 | 연결된 성공사례 → `/success/funding#case-<slug>` |

양방향으로 걸어 **문서 → 결과**, **결과 → 문서** 어느 쪽에서 들어와도 나머지 절반을 볼 수 있도록 구성.

**② -2. 선정 여부 배지**

`portfolioProjects` 항목에 결과 필드 신설. 값이 있는 건만 배지 노출, 없으면 기존과 동일하게 표시.

```ts
outcome?: {
  status: "selected" | "awarded" | "entered",   // 선정 | 낙찰 | 입점
  label: string,        // "TIPS 최종 선정"
  amount?: string,      // "8억 원"
  year: number,         // 2026
  caseSlug?: string,    // 성공사례 연결용
}
```

갤러리 카드 우상단에 `선정 · 8억 원` 형태로 배지 표시. 1절에서 확정한 원장과 값이 어긋나지 않도록 `success-ledger.ts`를 참조해 검증하는 테스트 추가.

**② -3. 화면 배치 — A4 세로 4장 가로 나열**

대표가 제시한 참고 형태는 A4 세로 장표 4장을 가로로 늘어놓고 좌우로 넘기는 캐러셀. 사업계획서가 A4 세로이므로 5절의 승인 목업 세트 중 `approved-a4-portrait-suite`가 그대로 대응. 따라서 PPT 포트폴리오와 사업계획서 샘플이 같은 시각 규칙을 공유하게 됨.

| 요소 | 규격 |
|---|---|
| 한 화면 노출 | A4 세로 4장 (모바일 1~2장) |
| 넘김 | 좌우 캐러셀 + 하단 점 표시 |
| 한 줄 카피 | `상담 시 업종에 맞는 실제 자료를 확인하실 수 있습니다` |
| 적용 세트 | `approved-a4-portrait-suite` — 최소 고유 장표 7장 |

카피가 중요한 이유는 **웹 공개 범위를 줄이면서 상담으로 넘기는 장치**이기 때문. 즉 웹에는 짜임새만 두고 실물은 대면에서 펼치는 방식이라, 기밀 부담과 상담 유도를 한 문장으로 동시 해결.

> 다만 참고 사례는 장표를 **작게 표시할 뿐 원본 해상도 파일을 그대로 올린 형태**로 보임. 이 경우 이미지를 내려받아 확대하면 본문이 그대로 읽힘. 표시 크기와 파일 해상도는 별개이므로 아래 ②-4를 반드시 함께 적용할 것.

**② -4. 되돌릴 수 없게 굽는 가림 처리**

원본 장표 일부를 가려 공개하되, **복원 불가능한 방식**으로 처리.

금지 사항부터 명확히 둠.

| 금지 | 이유 |
|---|---|
| CSS `filter: blur()` | 원본 이미지가 그대로 전송되므로 개발자도구에서 속성만 꺼도 원문 노출 |
| 약한 가우시안 블러 | 글자 획 정보가 남아 복원 도구로 판독 가능 |
| 모자이크(픽셀화) | 블록 단위 대조 공격에 취약. [Bishop Fox — 텍스트 가림에 픽셀화를 쓰지 말 것](https://bishopfox.com/blog/unredacter-tool-never-pixelation) |

따라서 **서버에서 구워낸 파생 이미지만** 저장소에 넣고, 원본은 추적 대상에서 제외.

처리 방식은 축소 후 확대와 블러의 이중 적용. 축소 단계에서 글자 정보가 물리적으로 소실되므로 되돌릴 근거 자체가 사라짐.

```
scripts/build-plan-samples.mjs

  입력  assets/plan-source/<id>/*.png        ← .gitignore 대상, 저장소 미포함
  처리  ① sharp.resize(원폭 / 12)             정보 소실 단계
        ② sharp.resize(원폭, { kernel: "nearest" })
        ③ sharp.blur(4)                      블록 경계 정리
        ④ webp 변환 (품질 78)
  출력  public/images/plan-samples/<id>/sample-01.webp ...
  검사  출력물에서 본문 판독 불가 여부 육안 확인 후 커밋
```

1600px 폭 장표를 1/12로 줄이면 본문 글자가 1픽셀 미만으로 무너지므로 판독 근거가 남지 않음. 반면 제목 크기 글자와 도형·색·배치는 형태가 남아 **문서 짜임새는 그대로 전달**.

**② -5. 설명은 캡션이 담당**

가린 이미지는 분위기만 전하므로, 실제 정보는 울림이 직접 쓴 캡션으로 전달. 따라서 좌표 지정 같은 수작업이 불필요하고 장표마다 의도를 명시 가능.

```ts
planSample: {
  images: [
    "/images/plan-samples/pamiti/sample-01.webp",
    "/images/plan-samples/pamiti/sample-02.webp",
    "/images/plan-samples/pamiti/sample-03.webp",
  ],
  captions: [
    "목차 — 평가항목 순서에 맞춰 8개 장으로 배열",
    "시장 규모 — TAM·SAM·SOM 3단계로 산정 근거 제시",
    "재무 계획 — 3개년 추정손익과 자금 사용 계획 연결",
  ],
  notice: "고객사 보호를 위해 본문을 판독 불가하게 처리한 화면입니다. 문서 짜임새 확인 용도로만 제공합니다.",
}
```

공개 장수는 프로젝트당 **3장 안팎**으로 제한. 전장 공개는 하지 않음.

**② -6. 입찰제안은 표지만**

입찰제안 건은 대부분 PPT이고 디자인 포트폴리오에 이미 등재된 상태. 그러므로 별도 샘플을 만들지 않고 **표지 1장 + 낙찰 결과 배지**로 갈음하며, 본문은 `/portfolio/ppt` 연결로 넘김.

| 구분 | 공개 범위 | 근거 |
|---|---|---|
| 사업계획서·IR | 가린 본문 3장 + 캡션 | 문서 짜임새가 구매 판단 요소 |
| 입찰제안 | 표지 1장 + 낙찰 배지 | 디자인 포트폴리오와 중복, 낙찰 사실이 핵심 |

**② -7. 공개 범위 문구 조정**

현재 `consultingCases` 4건에 `evidencePublic: false`와 함께 `홈페이지에 공개하지 않습니다` 문구가 고정돼 있음. 가린 샘플을 올리면 이 문구와 어긋나므로 세 값으로 세분.

```ts
evidenceLevel: "none" | "redacted" | "public"
// none     — 현행 유지, 아무것도 공개하지 않음
// redacted — 가린 샘플 공개. notice 문구를 그에 맞게 교체
// public   — 고객 동의 확보 건. 원본 공개
```

**② -8. [대표 확인] 공개 동의**

가림 처리는 **판독을 막을 뿐 공개 사실 자체를 없애지 못함**. 용역 계약에 비밀유지 조항이 있는 건은 가렸더라도 공개가 계약 위반이 될 수 있음. 그러므로 샘플 대상 선정 시 아래 셋을 먼저 확인할 것.

1. 계약서 비밀유지 조항 유무
2. 고객사 상호·로고·제품명이 가린 뒤에도 남는지 — 남으면 해당 장표 제외
3. 미공개 기술·재무 수치가 제목 크기로 적혀 있는지 — 제목은 가려도 형태가 남음

위험이 있는 건은 샘플 대상에서 빼고, 안전한 건 위주로 **3~5개 프로젝트만 우선 적용** 권고.

## 7. 플로팅 상담 바 — 화면 어디서든 닿는 상담 통로

### ① 현재 상태

상담 유도 장치가 `ContactBand` 하나뿐이며, 그마저도 각 화면 **맨 아래**에만 배치. 따라서 끝까지 내려간 방문자만 마주치고, 중간에서 이탈하는 방문자는 상담 통로를 한 번도 보지 못함.

상단 `Header`에도 상담 버튼이 없어, 화면 어느 지점에서든 닿는 상담 진입점이 부재한 상태.

### ② 바꿀 내용

**② -1. 형태**

| 요소 | 내용 |
|---|---|
| 배치 | 화면 하단 고정, 가운데 정렬, 알약형 카드 |
| 제목 | 화면 갈래별 문구 (아래 ②-3) |
| 부제 | 한 줄 보조 설명 |
| 버튼 | `상담 신청` → 해당 갈래 문의 화면 |
| 닫기 | 우측 X — 누르면 해당 세션 동안 숨김 |

**② -2. 등장과 퇴장 시점**

처음부터 띄우면 히어로 영역을 가리므로 일정 지점부터 등장시킴. 또한 하단 `ContactBand`가 보이는 구간에서는 같은 권유가 둘이 되므로 물러나게 처리.

```
스크롤 0 ────────── 400px ─────────── ContactBand 진입 ── Footer
   숨김              등장                   숨김            숨김
```

`IntersectionObserver`로 `ContactBand`와 `Footer`를 감시해 화면에 들어오는 순간 숨김. 스크롤 이벤트 직접 구독보다 부하가 낮고 끊김이 없음.

**② -3. 화면별 문구 — 3절과 연동**

디자인 화면에서 `지원금 진단` 문구가 뜨면 맥락이 어긋나므로, 현재 화면 갈래에 맞춰 문구와 연결 대상을 함께 바꿈.

| 화면 | 제목 | 연결 |
|---|---|---|
| `/services/consulting`, `/success/*` | 정부지원사업 자격 무료 1:1 진단 | `/contact/consulting` |
| `/services/business-docs`, `/portfolio/ppt`, `/portfolio/business-ir` | 사업계획서·제안서 상담 | `/contact/business-docs` |
| `/services/design`, `/portfolio/design` | 디자인 견적 문의 | `/contact/design` |
| 그 외 공개 화면 | 무엇이든 먼저 듣고 방향을 제안 | `/contact` |
| `/contact`, `/contact/*` | **노출하지 않음** | — |
| `/admin/*`, `/partner/*` | **노출하지 않음** | — |

문구는 3절의 `data/contact-tracks.ts`에 함께 두어 한 곳에서 관리. 그러므로 3절 미착수 시에는 전부 `/contact`로 연결되고, 3절 완료 후 자동으로 갈래별 연결로 전환.

**② -4. 콘텐츠 가림 방지**

하단 고정 요소는 마지막 콘텐츠를 덮으므로 보정 필수.

| 대상 | 처리 |
|---|---|
| 마지막 줄 가림 | 바 높이만큼 `body` 하단 여백 확보 |
| iOS Safari 하단 바 겹침 | `padding-bottom: calc(12px + env(safe-area-inset-bottom, 0px))` |
| 모바일 폭 부족 | 390px 이하에서 부제 숨기고 한 줄로 축약, 버튼 크기 축소 |

**② -5. 닫기 상태 보관**

`sessionStorage`에 보관. `localStorage`는 영구 보관이라 과하며, 다음 방문 때 다시 보여주는 편이 적절.

저장소 접근이 막힌 환경(시크릿 창, 사이트 데이터 차단)에서는 읽기·쓰기가 예외를 던지므로 `try/catch`로 감싸고, 실패 시 **그냥 노출**하는 쪽으로 처리.

**② -6. 접근성**

| 항목 | 처리 |
|---|---|
| 역할 | `role="complementary"` + `aria-label="상담 안내"` |
| 닫기 버튼 | `aria-label="상담 안내 닫기"` |
| 포커스 | 등장 시 자동 포커스 금지 — 읽던 자리를 빼앗지 않음 |
| 움직임 | `prefers-reduced-motion` 시 등장 전환 생략 |
| 대비 | 버튼 배경과 글자 명도 대비 4.5:1 이상 |

**② -7. 확정 문구 — 실적을 앞세우는 방향**

대표 확정안. 각 갈래가 자기 분야의 최대 실적을 앞세우고, 부제에서 문턱을 낮추는 배열.

| 갈래 | 제목 | 부제 | 제목 길이 |
|---|---|---|---|
| 컨설팅 | TIPS 8억까지, 지원사업 무료 진단 | 49억 선정·낙찰·투자를 만든 방식으로 봐드립니다 | 20자 |
| 비즈니스문서·PPT | 11억 낙찰을 만든 제안서, 상담부터 | 분량과 일정만 알려주시면 바로 안내드립니다 | 19자 |
| 디자인 | 브랜드에 맞는 디자인, 견적부터 | 로고부터 브로셔까지 한 번에 잡아드립니다 | 17자 |
| 공통 | 49억을 만든 방식, 먼저 들어보세요 | 계약하지 않으셔도 됩니다 | 19자 |

버튼 문구는 **`무료 상담`** 으로 통일. 문의 화면 안의 `상담 신청하기`와 겹치지 않으면서 비용 부담이 없다는 점을 한 번 더 전달.

제목은 390px 폭에서 한 줄을 유지해야 하므로 **한글 20자를 상한**으로 둠. 두 줄로 접히면 바 높이가 커져 가리는 면적이 늘어남.

**② -8. 숫자는 원장에서 가져올 것**

문구에 박힌 `49억`, `11억`, `8억`은 1절에서 확정한 값과 같아야 하며, 따로 적어 두면 원장이 갱신될 때 조용히 어긋남. 그러므로 문자열에 직접 쓰지 않고 치환자로 처리.

```ts
// data/contact-tracks.ts
floating: {
  consulting: {
    title: "TIPS {largestGrant}까지, 지원사업 무료 진단",
    subtitle: "{totalAchievement} 선정·낙찰을 만든 방식으로 봐드립니다",
  },
  // ...
}
// 치환값은 data/success-metrics.ts 에서 주입
```

따라서 **7절 착수는 1절 완료를 전제**로 함. 1절 이전에 손대면 아직 정정되지 않은 수치가 화면 전면에 노출됨.

**② -9. 유입 측정**

버튼 클릭 시 출발 화면 경로를 문의 폼으로 전달. 2절에서 만든 `source_path` 필드를 그대로 사용하므로 추가 설계 불필요. 이로써 어느 화면의 바가 실제 상담으로 이어지는지 확인 가능.

```
/services/consulting 에서 클릭
  → /contact/consulting?from=%2Fservices%2Fconsulting
  → contact_inquiries.source_path = "/services/consulting"
```

## 8. 고객사 표기 — 실명을 이니셜로 되돌리기

### ① 현재 상태

익명화 수준이 화면마다 어긋난 상태.

| 영역 | 현재 표기 | 건수 |
|---|---|---|
| `consultingCases` | 업종형 익명 (`AI 플랫폼 스타트업`) | 4 |
| `pptCases` | 업종형 익명 (`공공서비스 운영 기업`) | 10 |
| `portfolioProjects` | **전부 실명** | **50** |

`/success` 하단에는 이미 `모든 고객사는 업종형 익명명으로 표기하며` 문구가 걸려 있음. 그런데 포트폴리오는 실명이므로 같은 사이트 안에서 약속과 실제가 어긋남.

### ② 바꿀 내용

**② -1. 이니셜만으로는 구분 불가**

50건을 로마자 첫 글자로 줄이면 충돌이 대량 발생.

| 이니셜 | 충돌 건수 | 해당 기업 |
|---|---|---|
| M | 6 | MS글로벌 · 미래아이앤택 · 모노맨션 · 맨파워코리아 · 미사동커피 · 모란막걸리 |
| S | 5 | 수성별 · 삼성화재 · SK케미칼 · 선랑JDC · 더신선팜 |
| W · H · G | 각 4 | — |
| L · O · P · R · D · E · C · J · K | 각 2~3 | — |

따라서 이니셜 단독 표기는 불가하며, **이니셜 + 업종** 조합이 필수. 다행히 `industry` 필드가 50건 전부 채워져 있어 추가 입력 없이 해소 가능.

**② -2. 표기 규칙**

```
<로마자 첫 글자>사 · <업종>
```

| 원 상호 | 표기 |
|---|---|
| 온누리스토어 | `O사 · 건강기능식품` |
| ㈜킵유 | `K사 · 유통·판매` |
| 더블유포지션 | `W사 · IT·데이터` |
| 미사동커피공동체협동조합 | `M사 · 커피·제조·카페` |
| VAA | `V사 · 모델 에이전시` |

세부 규칙은 넷.

1. 법인격(`㈜`, `주식회사`, `유한회사`, `영화사`)을 떼고 남은 첫 글자를 취함
2. 한글 상호는 로마자 표기 첫 글자 — `건봉국밥` → `G`
3. 영문 상호는 그대로 — `WIZNMI` → `W`, `UYU` → `U`
4. 동일 기업의 복수 건은 같은 표기를 공유 — 파미티 3건, 미래아이앤택 2건

위 규칙 적용 시 50건 전부 고유하게 구분됨을 테스트로 검증.

**② -3. 실명을 남겨야 하는 곳 — 발주처와 입점처**

고객사와 **발주처·입점처는 성격이 다름**. 전자는 울림이 도운 기업이므로 가려야 하나, 후자는 실적의 값어치 그 자체이므로 가리면 실적이 죽음.

대표 확정 사항. 발주처·입점처는 실명을 남김.

| 구분 | 처리 | 예 |
|---|---|---|
| 고객사 | 이니셜 | `L사 · 가죽·패션` |
| 입점처·플랫폼 | **실명 유지** | 더현대 · CJ온스타일 · 카카오 선물하기 · 무신사 · 현대캐피탈 · 올리브영 · 다이소 · 홈플러스 |
| 발주기관 | **실명 유지** | 부산 금정구 · 광양시 · 부평소방서 · 롯데케미칼(대회 주최) |
| 발주 원청 | **실명 유지** | CJ올리브네트웍스 (SI 용역 발주처) |

`더현대 팝업 입점`을 `D백화점 입점`으로 바꾸면 문장이 아무것도 말하지 않게 됨. 그러므로 `L사(가죽·패션)의 카카오 선물하기 입점` 형태로, **가리는 쪽과 남기는 쪽을 한 문장 안에서 나눔**.

**② -4. 공공기관·대기업 고객사 — 확정**

대표 확정안은 **공공기관 실명 유지 · 대기업 이니셜**. 공공기관은 실적 공개가 비교적 자유로운 반면 대기업은 계약상 제약이 엄격한 편이므로, 신뢰 근거는 살리면서 위험은 피하는 배치.

| 기업·기관 | 업종 | 처리 | 표기 |
|---|---|---|---|
| 한국수자원공사 | 공공기관·환경 | 실명 유지 | `한국수자원공사` |
| 광주소방서 | 공공기관·안전 | 실명 유지 | `광주소방서` |
| 청곡종합사회복지관 | 공공기관·복지관 | 실명 유지 | `청곡종합사회복지관` |
| 한국건설직업전문학교 | 교육 | 실명 유지 | `한국건설직업전문학교` |
| 삼성화재 | 보험 | 이니셜 | `S사 · 보험` |
| SK케미칼 | 화학·제조 | 이니셜 | `S사 · 화학·제조` |
| 롯데웰푸드 | 키즈카페 | 이니셜 | `L사 · 키즈카페` |

이 판정을 코드에 박지 않고 데이터로 둘 것. 나중에 계약 상황이 바뀌면 값 하나만 고쳐 전환 가능.

```ts
// data/content.ts — portfolioProjects 각 항목
nameDisclosure: "public" | "initial"   // 기본값 "initial"
```

> 실명 유지 4건도 계약서 확인이 선행돼야 하며, 비밀유지 조항이 있으면 `initial`로 내릴 것.

**② -5. 이미지가 더 큰 문제**

텍스트만 이니셜로 바꾸고 이미지를 그대로 두면 익명화가 성립하지 않음. 현재 포트폴리오 목업에는 **고객사 로고·상호·제품명이 그대로 박혀 있음**.

> 예 — `onnuri-store/thumbnail.webp` 표지에 `PANTOMONA 판토모나` 제품명과 `온누리 Store` 로고가 선명하게 노출

따라서 이 절은 **5절(목업 교체)과 묶어 처리**해야 하며, 순서는 다음과 같음.

```
① 텍스트 이니셜화        — 즉시 가능, 이 절 단독
② 이미지 상호·로고 확인  — 50건 × 5장 육안 점검
③ 노출 건 처리           — 목업 재생성 시 해당 영역 가림, 또는 그 장표 제외
```

②를 건너뛰면 `O사`라고 적어 둔 카드의 썸네일에 상호가 그대로 보이는 상태가 됨. 즉 **텍스트만 바꾼 익명화는 익명화가 아님**.

**② -6. 검색 노출 영향**

실명이 빠지면 상호 검색 유입은 사라지나, 해당 검색량은 미미. 반면 `건강기능식품 브랜드 소개서` 같은 **업종 키워드는 오히려 표면으로 드러나** 유입에 유리. 단 `metadata`, `alt` 텍스트, `itemListSchema`에도 상호가 들어가므로 함께 교체할 것.

### ③ 건드릴 파일

```
신설  lib/anonymize.ts                  상호 → 이니셜 변환 + 충돌 검사
신설  lib/anonymize.test.mjs            50건 전부 고유함을 검증
수정  data/content.ts                   portfolioProjects company 필드
수정  data/success-ledger.ts            원장 기업명
수정  components/ProjectGallery.tsx     alt 텍스트, 대화상자 제목
수정  app/portfolio/*/page.tsx          metadata description
수정  lib/schema.ts                     itemListSchema 항목명
수정  app/success/page.tsx              하단 익명 표기 안내 문구
```

### ④ 완료 판정

- `lib/anonymize.test.mjs` 통과 — 50건 표기가 전부 고유, 동일 기업 복수 건은 동일 표기
- `nameDisclosure: "initial"` 인 항목의 원 상호가 화면 어디에도 없음 — `grep -rn "온누리스토어\|킵유\|더블유포지션\|파미티\|삼성화재\|SK케미칼\|롯데웰푸드" app/ data/ components/` 결과 0건
- `nameDisclosure: "public"` 4건(한국수자원공사·광주소방서·청곡종합사회복지관·한국건설직업전문학교)은 실명 그대로 노출
- 발주처·입점처 실명이 이니셜로 바뀌지 않았음을 검증하는 테스트 통과
- 페이지 원본(`view-source`)과 JSON-LD 어디에도 익명화 대상 상호가 없음
- `alt` 텍스트가 이니셜 표기를 따름
- 이미지 상호 노출 점검표가 작성되고, 노출 건이 5절 처리 대상으로 등록
- `npm run verify` 전체 통과

## 11. 후속 과제 — 실적 게시판 자동 반영 (보류)

울림웍스 실적 게시판(`hub.woolimcompany.kr/boards`)에 올라오는 실적을 홈페이지에 자동 반영하는 건은 **게시판 개편이 끝난 뒤로 보류**. 다만 지금 만드는 1절 원장이 나중에 게시판 데이터로 갈아끼워질 수 있도록 두 가지만 미리 지킬 것.

**① 원장 접근을 함수 하나로 감쌀 것**

화면들이 `success-ledger.ts` 배열을 직접 import하지 않고 `getSuccessLedger()` 함수만 거치게 함. 그러면 나중에 출처가 파일에서 DB로 바뀌어도 화면 코드는 그대로.

```ts
// 지금: 파일에서 읽음
export async function getSuccessLedger() { return SUCCESS_LEDGER; }
// 나중: 게시판 테이블에서 읽음 — 호출부 변경 없음
```

**② 원장 항목 형식을 게시판 칸과 맞출 것**

이번 정리에서 고친 오류 넷 — 근거 없는 건, 1차 합격을 최종으로 기재, 단위가 헷갈리는 금액, 고객사 실명 노출 — 은 전부 자유 서술 글이 그대로 올라가서 생긴 문제. 그러므로 게시판 개편 시 아래 칸을 갖추고, 원장 형식도 지금부터 같은 칸으로 맞춤.

| 칸 | 형식 | 이유 |
|---|---|---|
| 연도 | 숫자 | 기간 집계 |
| 사업명 | 글 | |
| 고객사 | 글 (내부용 실명) | 화면에는 8절 규칙으로 이니셜 변환 |
| 갈래 | 선택 — 지원사업·입찰·투자·입점·인증·수상 | 합계 분리 |
| 단계 | 선택 — 1차 통과·최종 확정 | **최종만 합계 산입** |
| 금액 | 숫자 (원 단위) | `5.5백만` 같은 표기 혼선 차단 |
| 공개 | 체크 | **대표 승인 전에는 홈페이지 합계 미반영** |

울림웍스 저장소 위치는 `#개발노트\daily-work-calendar`로 확인. 게시판 작업 착수 시 이 폴더를 연결해 같은 Supabase 프로젝트인지부터 확인하고, 경로를 정할 것.

| | 같은 Supabase 프로젝트 | 다른 프로젝트 |
|---|---|---|
| 방식 | 홈페이지가 공개 승인된 행만 읽는 보기(view) 하나 추가 | 게시판 저장 시 허브가 홈페이지로 알림 → 홈페이지 측 저장 |
| 작업량 | 작음 | 중간 |
