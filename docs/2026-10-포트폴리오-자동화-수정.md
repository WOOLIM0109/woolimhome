### 조사 결과 — 해당 원인 수정은 하지 않음

**흥국생명:** 원본 워커가 `TextRange.Font.Name`을 수집한 뒤 설치 글꼴의 `.Name`과 직접 비교한다. `+mn-ea`, `+mj-ea`를 minor/major East Asian 테마 참조로 해석하지 않아 설치 글꼴명처럼 누락 처리한다. 실제 PC 사용자 환경에서 `.Name=맑은 고딕`, `GetName(1033)=Malgun Gothic`, `GetName(1042)=맑은 고딕`을 읽기 전용으로 확인했다. 영어 선언과 한국어 설치명을 서로 다른 것으로 비교하는 것이 Malgun Gothic 누락의 원인이다. 수정안은 각 장표의 layout→master→theme 연결을 따라 실제 테마 글꼴을 결정하고, 영어·한국어 이름을 같은 family의 별칭으로 비교하는 것이다. 테마 해석 실패를 무조건 설치됨으로 처리하지 않는다. 새 준비 검사에는 이미 테마 연결 처리가 있으나 기존 변환 워커의 해당 로직은 이번에 수정하지 않았다. [FontFamily.GetName 문서](https://learn.microsoft.com/en-us/dotnet/api/system.drawing.fontfamily.getname), [Open XML MinorFont 문서](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.drawing.minorfont).

**현대실업:** 작업 `d273a7db-f937-4cba-b22e-fe78526985fc`는 9월 29일 KST 11:00:08, 11:01:29, 11:02:48에 claim됐고 각 실행에서 다운로드 3회를 시도한 뒤 3/3 한도로 실패했다. 변환을 시작하기 전 다운로드 단계의 오류이며 장표·검토 자산은 없다. `--fail` 사용 시 curl 22는 HTTP 400 이상 응답을 뜻한다. [curl 공식 오류 코드](https://curl.se/libcurl/c/libcurl-errors.html). 서버 claim은 매번 다운로드 URL을 다시 요청하므로 오래 대기한 최초 URL 만료라고 단정할 수 없다. 후보와 download 결과의 driveFileId는 일치하며 파일 크기는 74,386,758바이트다. 인덱스의 last_seen_at은 7월 27일로 오래됐지만 실제 원본 삭제·이동·권한 변경 증거는 없다. 당시 HTTP 상태·정제한 응답 코드가 로그에 없어 세부 원인은 미확정이다. 수정 제안은 비밀 URL·Authorization을 숨긴 HTTP 상태/최종 호스트/요청 ID 기록, 401·403 시 제한된 인증 갱신, 404 시 원본 메타데이터 재확인, 429·5xx만 제한 재시도다. 인증 우회나 무제한 재시도는 제안하지 않는다. 코드 변경·재다운로드·토큰 갱신은 하지 않았다.

**드림윙즈:** 실제 사용자 환경에서 `Test Söhne`와 `Work Sans` 계열을 확인했다. 원본의 `Söhne`와 `Test Söhne`는 기존 비교에서도 같은 이름이 아니다. 현재 사용자 레지스트리로 기존 알고리즘의 지문을 계산한 값은 `f23f634a66af6c117687126ca8941ae4eb3b57f9ed1812294eaa7226c77c3780`이며 운영 워커와 후보가 보유한 지문과 같다. 따라서 현재 읽은 상태에서는 설치 변경 재시도 조건을 충족하지 않는다. 작업 `3d39b9fd-c8cc-464f-a782-448447b094dd`는 9월 22일 KST 09:08:38 이후 갱신되지 않았고 attempts=1, on_hold, missing_fonts=`Work Sans SemiBold,Söhne`다. worker.log에도 해당 작업의 이후 claim이 없다. 연결 검토 자산 0건, 작업·후보 ID를 포함한 저장소 객체 0건이다. **운영 기록상 자동 재요청·산출물 생성은 확인되지 않았다.** 원본은 과거 실패 후 로컬 삭제 로그가 있으며, 임의로 워커를 재시작하거나 하트비트를 보내 재시도를 유발하지 않았다. 초기 샌드박스 계정의 글꼴 목록과 실제 PC 사용자 목록이 달라 최종 판정에는 후자를 사용했다.

### 유료 글꼴 규칙의 보수적 판단

설정은 `lib/portfolio/font-policy.ts`의 `UNOWNED_PAID_FONT_FAMILIES`다. Söhne의 스타일명·Test 접두사·분해된 악센트/영문 표기를 포함해 차단한다. 후보 선정 전에 PPTX XML의 글꼴 선언을 읽으며, 변환 요청은 하지 않는다. 사용하지 않는 테마·마스터에 남은 선언도 포함해 제외한다. 오탐 가능성이 있지만 구매하지 않는 글꼴이 제작에 들어가는 위험을 줄이기 위해 선택했다. 원본에서 해당 선언을 제거하고 재검토하기 전 자동으로 해제하지 않는다.

PDF/PPT처럼 이 단계에서 글꼴을 검증할 수 없는 파일, 손상·과대 XML·글꼴 선언 없는 파일은 검수 대상으로 남긴다. 설치 파일 존재만으로 라이선스를 가진 것으로 간주하지 않는다. 운영 후보 상태는 이번에 쓰지 않았으므로 드림윙즈 카드가 이미 제외로 바뀌었다고 보고하지 않는다.

실제 PC 사용자 환경에서 새 `Get-FontInventory` 함수와 해시 보조 함수만 독립 실행했다. Test 계열 반환 0개, Work Sans 인식 1개, 전체 family 1,114개·파일 1,229개와 지문 생성 성공을 확인했다. PowerPoint·변환·하트비트·운영 API 호출은 하지 않았다. 이는 실제 글꼴 목록 함수 확인이며 포트폴리오 운영 제작 성공 검증과 구분한다. 글꼴 정책·PPTX 검사 대상 테스트 25개도 통과했다.

## 변경 내용

- 목업 완료 후 Gemini가 켜져 있으면 본문 작업을 `queued`로 연결한다. 실제 생성은 기존 `runBudgetedGeminiAutomation`을 통과한다. 꺼짐·호출 상한·실제 오류는 `draft_waiting`과 원래 오류 코드/문구로 남는다. 실패 후 자동 재시도는 중단하고, 체크포인트 양보도 최대 시도 횟수 안에서만 이어간다.
- 발행 원장에는 정규화 프로젝트명, 글 URL·제목·발행일, 드라이브 파일·후보·작업 연결, 대표 이미지 해시, 출처를 보관한다. RLS와 권한 회수로 anon/authenticated 접근을 차단했다. 관리자·파트너 발행 완료 시 상태 변경과 원장 기록을 같은 DB 트랜잭션에서 처리한다. URL 충돌 시 발행 변경도 취소된다.
- 후보 카드의 **이미 블로그에 있음**에서 URL·제목을 입력하면 원장 등록과 후보 제외를 함께 처리한다. 제작 중이거나 다른 작업에 연결된 후보는 수동 제외를 거부한다.
- 정규화 이름, 기존 제작 후보, 발행 원장, 기존 발행 작업의 원본명, image set 및 대표 이미지 해시를 먼저 대조한다. 통과한 후보만 작업과 대기열을 만든다. 원본 이미지 근거를 읽을 수 없으면 PC 변환부터 시도하지 않고 검수 대상으로 남긴다.
- 같은 프로젝트는 PPTX → 최신 수정일 → 사본 후순위로 하나만 남긴다. 중복 사유는 `중복: 기존 제목 (URL 또는 후보 ID)`로 저장하고, 점수는 이름 일치 100 또는 `round((1 - 해밍거리 / 64) × 100)`으로 계산한다.
- 후보 예약 시 DB 잠금 안에서 이름·해시를 다시 검사하고 후보 선택·작업·6단계 대기열 생성을 원자적으로 처리한다. 다른 실행에서 먼저 선택했거나 자식 작업 생성에 실패하면 반쪽짜리 제작 상태를 남기지 않는다.
- 화면은 본문 작성 대기 / 글꼴 대기 / 변환 실패(재시도 한도) / 중복 제외 / 검수 필요를 구분한다. 빠진 글꼴은 접힌 작업 카드에서도 보이고, 중복 대상은 후보 카드에서 링크로 확인한다.
- 금요일 `design-fri`를 제거한다. 화요일 09:00 포트폴리오와 목요일 09:00 기획·디자인 콘텐츠는 유지한다. 드라이브 사전 동기화와 PC 안내도 화요일 기준으로 맞춘다.

`portfolio_automation_control`은 기본적으로 첫 제작 미승인 상태다. 정리·미리보기 확인·해시 기준 승인 전에는 새 제작과 PC 변환을 막는다. 이 상태를 변경하는 운영 SQL은 아직 실행하지 않았다.

## 승인 후 실행 순서

1. 위 dry-run 9건·687개 객체와 과거 이력 CSV를 검토한다. 이력 적재 승인은 삭제 승인과 별개다.
2. 준비된 마이그레이션의 운영 적용을 승인받는다. `draft_waiting`, 원장, 등록 트리거/RPC, 중복 차단·첫 제작 잠금, 정리 RPC를 순서대로 적용해야 한다. 기존 원장 이력은 자동 적재하지 않는다.
3. PR을 통해 작업 1~5와 정리용 API/RPC를 main에 반영·배포한다. 이 작업 브랜치에서 main을 직접 수정하거나 push하지 않는다. 첫 제작 잠금은 계속 유지한다.

6. `node scripts/purge-naver-design-on-hold.mjs --execute --approval <승인파일> --env-file <서버접속설정>`을 실행한다. 실행 직전 새 백업을 만들고, DB 행과 저장소 삭제 결과를 각각 저장한다. 마지막에 DB와 `/admin/naver-design`에서 보류 0건을 확인한다.

## 검증과 운영 확인의 구분

코드 검증은 각 커밋의 `npm run verify`(타입 검사·ESLint·전체 테스트)로 수행한다. 본문 오류 테스트는 fetch stub만 사용하며 실제 Gemini를 호출하지 않는다. 원장 권한·충돌 시 롤백·후보 원자 예약·미검수 PC 차단·백업 변경 시 삭제 거부·공유 image set 보존은 메모리 내 PostgreSQL(PGlite)에서 검사한다. 실제 운영 DB에 테스트 쓰기를 하지 않는다.
