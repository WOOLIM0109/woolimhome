# 바뀐 마이그레이션 번호를 가리키는 곳을 고친다

## 무슨 일이 있었나

번호가 겹친 마이그레이션 파일 2개에 각자 번호를 줬습니다. 지금 브랜치 `fix/migration-version-collision-20261106` 에 그 이름 변경이 들어 있습니다.

- `multi_pc_workers.sql`의 번호 `202608040008` → `202608040018` (현재 파일: `202608040018_multi_pc_workers.sql`)
- `operational_hardening.sql`의 번호 `202608040009` → `202608040019` (현재 파일: `202608040019_operational_hardening.sql`)

그런데 옛 이름을 글자 그대로 적어 둔 곳이 남아 있어서 검사가 7개 떨어집니다. 아래는 변경 전 경로를 생략한 당시 오류입니다.

```

```

## 할 일

옛 이름을 새 이름으로 바꾼다. 아래 세 곳이 전부다.

| 파일 | 줄 | 바꿀 것 |
|---|---|---|
| `lib/naver-works/portfolio-produce.test.mjs` | 13 | `operational_hardening.sql`의 번호 `202608040009` → `202608040019` |
| `docs/2026-10-포트폴리오-자동화-수정.md` | 310, 313 | `multi_pc_workers.sql`의 번호 `202608040008` → `202608040018`, `operational_hardening.sql`의 번호 `202608040009` → `202608040019` |
| `tools/woolim-pc-worker/README.md` | 32 | `multi_pc_workers.sql`의 번호 `202608040008` → `202608040018` |

## 지키는 선

- **SQL 파일 내용은 손대지 않는다.** 이름만 이미 바뀌어 있고, 안에 든 명령은 그대로다.
- **파일 이름을 더 바꾸지 않는다.** 운영 DB 기록표가 이미 `…0018`, `…0019` 로 맞춰져 있다. 여기서 또 바꾸면 다시 어긋난다.
- `.codex-tmp/` 밑에 있는 사본은 건드리지 않는다. 다른 작업용 복사본이다.
- 옛 이름이 다른 곳에 더 남아 있는지 한 번 더 찾아보고, 있으면 같이 고치고 보고에 적는다.

## 끝났는지 보는 법

1. `npm run verify` 를 돌려 `portfolio-produce.test.mjs` 가 통과하는지 본다.
2. `grep -rn "20260804000[8]_multi_pc_workers\|20260804000[9]_operational_hardening" --include=* . | grep -v node_modules | grep -v .codex-tmp` 이 아무것도 못 찾아야 한다. 검색식 자체가 일치하지 않도록 같은 뜻의 문자 클래스를 사용하고, 이 문서의 변경 전 이름은 번호와 역할을 나누어 기록한다.

## 보고에 적을 것

- `npm run verify` 결과. 떨어진 게 있으면 이름과 메시지를 그대로 적는다.
