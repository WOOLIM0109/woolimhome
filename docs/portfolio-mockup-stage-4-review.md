# 묶음 4 — 승인 장표 배정·초안·최종본 검수

날짜: 2026-09-07  
판정: **로컬 구현·검수 완료. 운영 연결·배포 완료가 아님.**

## 1. 만든 기능

- 승인된 고정 템플릿 3세트의 썸네일·BODY 1~4 배정 화면.
- 원본 장표 번호, 슬롯 번호, 대표/보조 역할과 처리 상태 표시.
- 승인된 블러본만 선택·합성. 가림 전 PNG나 오래된 승인본을 대신 사용하지 않음.
- 장표 교체, 중복·빈 슬롯·부족 사유 표시, 배정표 저장.
- 한 배정표에서 직접 만드는 0.5배 초안과 1배 최종 PNG.
- 개별 확대, 기준선/슬롯 번호 보기, 현재 최종 PNG 내려받기.
- 변경된 목업만 다시 제작. 저장만으로 렌더링하거나 외부 API를 호출하지 않음.
- 새 장표 준비 요청과 사유를 로컬 기록으로 저장. **요청 소비·자동 변환 실행은 아직 미연결.**

목업 틀의 좌표·배경·각도·여백·로고·그림자는 이 묶음에서 변경하지 않았다. 1번 묶음에서 고정한 정의를 그대로 사용한다. 16:9와 A4 가로/세로 모두 썸네일은 1080×1080, BODY는 1600×900이며 초안은 각각 정확히 절반 크기다.

## 2. 실제 연결한 경계와 실패 규칙

입력은 묶음 3의 실제 가림 서비스가 만든 PNG다. 원본/제작 시도, 준비 단계 지문, 장표 번호, 가림 규칙과 수정 지문, 승인 시각, 출력 파일 지문을 다시 확인한 다음 목업에 넣는다. 이번 시각 검수의 원자료는 가짜 이메일을 포함한 합성 장표이며 고객 원본이 아니다.

- 지정된 표지가 준비되지 않았거나 미승인이면 해당 자리를 비워 사유를 표시한다. 다른 장표로 조용히 대체하지 않는다. 사용자가 직접 다른 승인본을 선택하는 것은 가능하다.
- 한 목업 안에서는 같은 원본 번호 또는 동일 PNG의 중복을 차단한다. 목업 사이의 장표 재사용은 허용한다.
- 규격이 다른 장표, 정의와 다른 슬롯, 다른 작업의 장표를 넣을 수 없다.
- 원본/가림/승인 정보가 달라지면 이를 사용하는 목업을 보류한다. 재제작이 오래된 승인을 자동으로 승계하지 않는다.
- 동시 수정은 revision 충돌로 거절한다. 브라우저의 저장·제작 중에는 편집을 잠근다.
- 최종본은 현재 배정표의 유효한 초안이 있어야 제작할 수 있다.
- 제작 도중 뒤쪽 목업에서 실패해도 먼저 완료한 목업 기록은 보존한다. 사용자가 다시 실행하면 필요한 목업부터 처리한다. 무한·백그라운드 재시도는 없다.
- 다운로드 시점에도 현재 승인과 PNG/제작 명세 지문을 검증한다. 이전 버전·변조 파일은 제공하지 않는다.
- 현재 운영 이미지 참조인 `activeSetRef`는 변경하지 않는다.

배정 지문은 초안과 최종본이 공유한다. 실제 렌더 지문에는 배율·PNG 형식도 포함해 두 출력이 서로 바뀌어 재사용되지 않게 했다. 템플릿 정의 외에도 렌더 코드, 로고·배경·폰트 파일과 Sharp 버전을 반영한다.

초안·최종 비교는 슬롯 모서리·기준점·레이어 순서·그림자·로고·허용 잘림을 검사한다. 같은 반올림 전 좌표에서 직접 렌더링하며, 논리 좌표와 배율 환산값의 오차를 검사한다. 회전 이미지 가장자리의 안티앨리어싱 여유 픽셀은 실제 정수 배치/잘림 명세에 별도로 기록한다. 그 여유 경계까지 무조건 1px 이내라고 주장하지 않는다.

## 4. 실제 이미지 시각 검수

규격별 합성 장표 10장을 긴 변 2400px로 준비했다. 16:9는 2400×1350, A4 가로는 2400×1697, A4 세로는 1697×2400이다. 실제 가림·승인 서비스에서 가짜 이메일 부분을 가린 뒤 제작했다. 이번 묶음에서 PowerPoint를 새로 실행하거나 고객 PPT를 변환하지는 않았다.

Codex가 다음 파일을 실제로 열어 확인했다.

| 대상 | 수량 | 확인 내용 |
| --- | --- | --- |
| 16:9 썸네일·BODY 1~4 | 5장 | 모든 슬롯 채움, 앞뒤 레이어, 평행, 그림자, 로고, 제목 |
| A4 가로 썸네일·BODY 1~4 | 5장 | 비율 보존, 평행, 간격, 고정 효과 |
| A4 세로 썸네일·BODY 1~4 | 5장 | 세로 비율, BODY 4 두 장의 공통 윗변/아랫변 직선 정렬 |
| 세트별 모아보기 | 3개 | 세트 내 시각 일관성과 교체 장표 배치 |
| 기준선 예시 | 3장 | 16:9 썸네일, A4 가로 BODY 2, A4 세로 BODY 4의 슬롯 경계/공통 직선 |
| 브라우저 교체 후 BODY 3·모아보기 | 각 1개 | 교체 장표 번호, 동일 배치·효과, 나머지 결과 보존 |

파일은 저장소의 무시된 `.codex-tmp/mockup-stage-4/`에 있다. `wide-*`, `landscape-*`, `portrait-*`가 원래 검수 결과이고, `wide-3-after-swap.png`와 `wide-sheet-after-swap.png`가 브라우저 교체 후 결과다. `results.json`과 `swap-proof.json`은 로컬 검수 기록이다. 합성 장표의 단순한 도형/큰 빈 영역은 시험 자료의 구성이지 고객 디자인 재현 결과가 아니다.

새로 생성한 일반 작업의 상태는 계속 `visualReview: not_performed`다. 이번 합성 QA를 열어 본 사실은 이 문서에만 기록하며, 이를 모든 후속 작업의 Codex 검수 완료로 자동 표시하지 않는다.

## 5. 브라우저 상호작용 검수

실제 로컬 화면에서 다음을 직접 조작했다.

1. 승인 후보 10장과 최종 목업 5장의 이미지 로딩 확인.
2. BODY 3 첫 슬롯을 이미 사용 중인 3번 장표로 바꾸자 중복 사유가 즉시 표시되고 저장/제작이 차단됨.
3. 해당 슬롯을 2번에서 1번 장표로 교체하고 저장. 저장 중 선택 입력이 잠기는 것 확인.
4. 저장 후 BODY 3만 초안/최종본 재제작 대상으로 바뀌고 다른 네 장의 다운로드 유지.
5. 초안과 최종본을 명시적으로 제작. BODY 3의 원본 번호는 `[1,3,4,5]`이고 다른 목업은 변경 없음.
6. 확대 화면, 기준선 표시와 일반 화면 전환 확인. 기준선을 켜도 다운로드 링크는 일반 최종 PNG를 가리킴.
7. 최종 다운로드 버튼 조작. 실제 OS 다운로드 파일의 저장 위치/완료 여부는 확인하지 않았으므로 파일 수신 완료로 기록하지 않는다. 응답 파일/헤더는 자동 HTTP 테스트로 검증했다.
8. 최종 상태에서 썸네일 1080px, BODY 4개 각각 1600px 자연 너비로 모두 로딩됨. 페이지 가로 넘침 없음.

서비스에서 현재 파일을 다시 읽어 대조한 결과: BODY 3만 지문이 달라졌고 나머지 네 장은 바이트 지문이 동일했다.

```text
BODY 3 이전: 5bf26cc33e4362e9e03ffe90d38d646abf119715679088e0d1e0cb7e9e1fa596
BODY 3 이후: 9652da62ae73579ba1fa4ecc4f59ad72e5731aab05151071502b2096115ae2e4
나머지 4장 변경: false
activeSetUnchanged: true
```

## 6. 구현 위치

- `lib/pc-worker/preparation/mockup-types.ts`: 배정/승인 지문/초안·최종 기록 계약.
- `lib/pc-worker/preparation/mockup-service.ts`: 승인본 검증, 배정 저장, 부분 제작, 실패 복구, 다운로드 검증.
- `lib/pc-worker/preparation/redaction-service.ts`: 배정 시 여러 승인본을 공통 준비 검사 후 검증하는 내부 연결. 기존 가림 승인 조건은 유지.
- `lib/portfolio/approved-assigned-board-renderer.ts`: 지정 슬롯 직접 합성, 제작 명세, 초안·최종 비교, 기준선 이미지.
- `lib/portfolio/approved-16x9-renderer.ts`: 기존 진입점 기본값을 유지한 배율/PNG 확장.
- `lib/pc-worker/preparation/local-review-server.ts`, `mockup-editor-client.mjs`: 로컬 `/mockups` 화면과 제한된 API.
- 대응하는 서비스·서버·렌더러 테스트와 `mockup-fixture.mjs`: 합성 데이터 기반 회귀 검사.
